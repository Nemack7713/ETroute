## One tap, isolated requests

The API 35 phone has reported passing startup, interruption, ST08 completion/lifecycle evidence and v6 simulated receipt-loss retention checks. The next acceptance APK chains those fixed cases without overlapping owners or enabling general scripts. One deliberate tap approves the fixed list; every evidence probe still creates and consumes its own coordinator capability. No user commands or module lists are accepted.

| Order | Case | Completion boundary |
| --- | --- | --- |
| 1 | ST01 before attachment | Confirmed no child started; owner and report finalized |
| 2 | ST02 active Stop | Native return, confirmed termination, watcher ended, report finalized |
| 3 | ST03 repeated Stop | Same boundary; cancellation count remains one |
| 4 | ST04 timeout | Native timeout/termination confirmed; watcher and report ended |
| 5 | ST07 normal completion | Exit zero; owner released and report finalized |
| 6 | ST08 completion evidence | Coordinator validation and replay rejection completed; owner released |
| 7 | ST05/ST08 lifecycle | Private child Activity destruction completed, native termination confirmed, worker finished and evidence validated |
| 8 | ST06 simulated receipt loss | Actual native completion confirmed; owner receipt withheld; snapshot and retry-block checks finalized |

The lifecycle check deliberately destroys a separate non-exported child Activity. The parent waits for a worker completion future **and** completed `onDestroy`, not an Activity-result callback or disappearance of the screen. The child accepts only an in-process, single-attachment slot token from the parent. It cannot accept arbitrary launch parameters. Missing completion triggers explicit cancellation and a bounded additional wait, then halts; a deadline is never a completion receipt.

## Barriers and failure policy

Each synchronous step returns only after native execution, readiness watcher shutdown, owner finalization and bounded per-step reporting. The chain then persists the step result before starting the next. A pass marker alone is insufficient: the adapter also requires a completion boundary and permission to advance. Legacy pre-attachment cancellation is a no-child boundary, not a claim of child termination. Evidence callbacks remain bound to the existing semantic validator.

A failed assertion, exception, missing barrier, unconfirmed termination or operator Stop halts the sequence; later cases are `NOT_RUN`. Stop is latched and explicitly signals the currently owned native request, independently of evidence. It does not advance, delete files or claim termination. A stopped step is labelled `INTERRUPTED`; the native result remains in its detailed report. Normal completion disables Stop with **NO ACTIVE CHAIN** feedback.

Simulated receipt loss is last because it sets the persistent uncertainty marker. Its native process actually ends and the owner is released, but it deliberately does not permit another native case. Only read-only retention inspection follows inside that terminal step. A fully passing chain reports `SEQUENTIAL_CHAIN=PASS_RETRY_BLOCKED`. This does not close genuine native-uncertainty testing. No later native test may follow that terminal retained outcome.

The report includes a same-run retention check; that is not reopening or process-death evidence. After closing and reopening the app, use the separate read-only retention button. The chain never resumes or restarts automatically. Destroying the parent requests Stop. Backgrounding alone retains the bounded current chain; no new service or background-restart mechanism is added. Android may prevent launching the lifecycle child from background; that fails or times out the barrier and halts the chain.

## Retention and limits

A persistent chain claim is committed before dispatch. This dedicated acceptance app allows one chain; failures and process death keep it claimed so a second run cannot overlap an unresolved owner. There is no reset or reconciliation bypass. Each case owns a fresh session, independent controller and bounded diagnostics. Existing eight-evidence-session and twelve-interruption-session caps remain; the chain uses five interruption and three evidence sessions.

There are eight step reports capped at 24,000 bytes each and a 16,000-byte summary. Reports are atomically renamed after bounded writes. Per-step native limits remain unchanged: fixed worker, absolute executable, 3-second timeout test and 10-second ordinary wall-time limits, bounded stdout/stderr and RLIMIT settings. Readiness watchers must end before a step can return. Artifacts are retained; cleanup is not asserted.

Install **ETroute Sequential Checks v7** alongside the previous apps. Tap **RUN FIXED TEST CHAIN** once. A lifecycle child screen briefly appears and closes automatically; wait for the parent summary. Expect eight passes with `barrierReached=true` and final `PASS_RETRY_BLOCKED`. The last step has `permitsNext=false` intentionally. Paste the summary; detailed reports are available separately.

Then close and reopen the app and tap **VERIFY RETENTION AFTER REOPEN**. Expect retained hashes/directories and the uncertainty marker to remain intact. Run stays disabled intentionally. General scripts remain disabled throughout. Do not clear prior apps to run this chain.

A full-chain instrumentation test exercises the real coordinator, native Stop/timeouts and actual child destruction; run it alone on a fresh chain-check installation. ## Failed-run diagnostics (v8)

The user-reported v7 chain passed ST01, ST02, ST03, ST04 and ST07, then returned `ST08_COMPLETE=FAIL` with coordinator `RUNNER_ERROR`. The summary marked the step interrupted and the chain stopped; the lifecycle and receipt-loss steps were not run. This proves that the chain halted, but the old report cannot identify the exception or the source of Stop. It does not establish whether native execution had started or terminated.

V8 retains a bounded runner failure report: phase, up to three exception causes with two stack frames each, owner Stop/destruction flags, Java thread interruption and actual native-return fields when available. The formatter is capped at 4,096 UTF-8 bytes; the optional session/error-file wrapper remains below 8 KiB. A failure still rejects through the existing coordinator. Diagnostic text is not a validated envelope or authorization receipt. Best-effort diagnostic persistence cannot gate cancellation or turn a rejection into acceptance.

The first chain Stop source is recorded atomically: operator button, parent destruction (finishing/configuration/other), or an aborted lifecycle launch. The record includes the current case. Normal finalization uses a separate close path and cannot invent an operator Stop; later destruction cannot overwrite an earlier cause. The summary includes `chainStopCause` and `chainStopStep`; an optional 1 KiB stop record joins the eight test reports. Therefore report display permits at most nine files. The strict sequential completion gates are unchanged.

A separately identified cancellation path is also corrected: native cancellation at entry can return CANCELLED with no exit, signal, errno or timeout before creating log files. That known no-child result now supplies empty missing streams and records unsuccessful `not-started` evidence, rather than throwing a missing-log exception. It does not claim child termination, and it never passes a completion test. Genuine cleanup uncertainty or a nonzero spawn errno does not qualify. This is a reproducible code-path correction; the supplied v7 report does not prove it caused that device failure.

Install **ETroute Chain Diagnostics v8** alongside v7, keep the app foreground and wait for the summary without pressing Stop. Do not clear v7 data. If the new run halts, send the summary and ST08 report, which now preserve the failure phase and Stop source. A passing path still requires phone confirmation. General scripts remain disabled, and no retry/reset bypass is added.

Additional JVM tests cover bounded failure text, missing native returns, underlying exceptions, known no-child cancellation, semantic not-started evidence, first-stop preservation, normal finalization and concurrent Stop sources. Instrumentation is compiled in CI; it is not presented as physical execution.

## Three-line error context (v9)

Exception reports now include a source excerpt when a stack frame can be matched unambiguously to the Kotlin source bundled with that debug APK. Each excerpt contains exactly three code rows: the preceding line, the reported error line marked `>`, and the following line. The header identifies the source path, line number, source SHA-256 and exception type. Start/end-of-file boundaries are explicitly labelled; they are not invented source lines. Very long lines are labelled as truncated.

The build snapshots project-owned main Kotlin sources from the library and validator, using a generated debug-only asset. It excludes build configuration, keys, credentials, test sources and third-party dependencies. CI verifies that every packaged hash and line array matches the checked-out source. The index is bounded to 128 files, 1 MiB input and 2 MiB JSON; a rendered excerpt is bounded to 6 KiB. Failure text plus an excerpt remains inside the existing 24,000-byte step report bound. Failure-file wrappers with source context remain below 12 KiB. Release APKs do not bundle this debug source index.

The resolver examines up to three exception causes and 32 frames per cause. A mapped first frame is labelled **EXCEPTION_LOCATION**. If the original throw site is outside the bundled source, a mapped application frame is labelled **APPLICATION_CALL_SITE**, with an explicit explanation. An ambiguous filename/package, missing or synthetic line number, native-only error, or typed failure without an exception produces **SOURCE_CONTEXT_UNAVAILABLE**. No arbitrary line is guessed. The excerpt locates an exception or call site; it does not itself prove a defect in that line.

The same source context is attached to fixed-probe runner exceptions, legacy interruption exceptions, chain action exceptions, lifecycle-host exceptions and parent chain exceptions. Non-exception native/validation outcomes explicitly state that no mapped exception location is available. Source diagnostics never replace evidence validation or weaken a completion barrier.

**ETroute Error Context v9** installs alongside earlier apps. Run the fixed chain and send its summary plus any failed test report. Four JVM regression tests verify exact three-row ordering, boundary labels, ambiguous/synthetic locations and external-call-site labels. An instrumentation fixture verifies loading and rendering the actual APK's source asset; CI compiles it rather than claiming physical execution. No general script execution, reset or merge is enabled by this update.


## Registry rejection diagnostics (v10)

A registry rejection reports its specific claim or issuance reason. Claim failures include the dispatch-preflight duration and configured authorization TTL. Expiry during repeated admission checks is a candidate to investigate, not an established explanation for the v9 phone result. Expired, revoked, mismatched or replayed claims still fail closed before the runner. No TTL extension, automatic retry or authorization refund is introduced.

Typed registry rejections include a captured source location labeled `REJECTION_GATE`, with the preceding line, rejecting line and following line. This is the enforcing check, not a thrown exception or a claim that the gate is defective. Source locations are mapped against the debug APK source snapshot.

The v10 app has a separate identity and preserves v9 reports. JVM regression tests cover expiry before and during dispatch preflight, no runner invocation and terminal replay rejection. Physical-device acceptance remains pending. General scripts remain disabled.
